## EXPLAIN

### 1. 기본 용어

| 용어 | 뜻 |
|---|---|
| 스마트팩토리 | 센서·데이터·AI로 공정을 실시간으로 보고 제어하는 공장. 사람이 일일이 순회하지 않아도 설비 상태를 데이터로 안다 |
| 자동차 4대 공정 | 프레스(패널 성형) → 차체(용접으로 골격) → 도장(세척·전착·도색·건조) → 조립(부품 장착). 한 곳이 서면 라인 전체가 선다 |
| 예지보전 (예측 정비) | 고장 난 뒤 고치거나 주기마다 교체하는 대신, 센서로 고장 징후를 미리 감지해 정비 시점을 정하는 것. 상태 기반 정비(CBM)라고도 한다 |
| 다변수 센서 데이터 | 진동·온도·압력처럼 여러 변수를 같은 시각에 함께 기록한 데이터. 한 변수가 놓친 이상을 다른 변수가 잡는다 |
| 진동 (mm/s) | 베어링·회전체 마모, 정렬 불량을 본다. 갑작스러운 증가나 추세적 상승이 전조 |
| 온도 (℃) | 마찰·과부하·윤활 부족을 본다. 서서히 오르는 흐름이 위험 신호 |
| 압력 (bar) | 유압·공압 계통의 누출·막힘을 본다. 평상 범위를 벗어나는 구간을 표시 |

### 2. 유지보수는 네 단계로 진화했다

무엇을 기준으로 정비하느냐가 단계를 가른다.

| 단계 | 정비 기준 | 특징 |
|---|---|---|
| ① 사후 정비 | 고장 발생 후 | 계획 불가 — 라인이 갑자기 멈춘다. 손실 최대 |
| ② 예방 정비 (TBM) | 정해진 시간·주기 | 상태와 무관하게 교체 — 안전하지만 멀쩡한 부품도 버린다 |
| ③ 예측 정비 (CBM, 예지보전) | 센서가 감지한 징후 | 필요할 때만 정비 — 비용과 라인 정지를 함께 줄인다 |
| ④ 처방 정비 | AI 원인 진단·조치 | 무엇을 어떻게 고칠지까지 제안한다 |

### 3. 케이스 — 열어 볼 수 없으면 둘러싼 신호를 읽어라

포스코 포항제철소의 고로(용광로)는 한 번 불을 붙이면 십수 년을 멈추지 않고, 내부는 1,500℃라 사람이 들여다볼 수 없다. 예전에는 수십 년 경력의 명장이 불꽃 색과 소리로 노의 컨디션을 읽었고, 그 감은 퇴직과 함께 사라졌다. 노 곳곳의 센서·조업 데이터를 모아 AI가 쇳물 온도를 예측하게 하자 명장의 판단이 데이터로 남았고, 2019년 세계경제포럼(WEF)이 국내 최초의 '등대공장'으로 선정했다. 직접 못 재는 상태를 주변 신호로 추정하는 것 — 오늘 진동·온도·압력을 함께 보는 이유다.

### 4. 단위가 섞이면 이상 판단이 흔들린다

원본 강의는 데이터 단계에서 "단위(℃, mm/s, bar)와 측정 주기를 먼저 확인하라"고 했다. 로거(기록장치)를 교체하거나 휴대용 측정기를 쓰면 미국식 단위(℉, in/s, psi)로 찍히는 일이 실제로 있다. 온도 50℃가 122℉로 찍히면 평균 52℃인 설비에서 "70도 넘게 튄 이상"처럼 보인다. 이상을 찾기 전에 **단위부터 맞춘다.**

| 환산 | 식 |
|---|---|
| ℉ → ℃ | (℉ − 32) × 5 / 9 |
| in/s → mm/s | × 25.4 |
| psi → bar | × 0.0689476 |

## EXECUTE

아래 프롬프트를 붙여 넣으라고 안내한다.

```
pdm-lab 폴더에서 데이터 점검을 해 줘.

1. data/Day5_예지보전_도입사례_실데이터.csv 를 읽고 [기업 / 설비 / 사용 센서 / 예측 대상 / 보고된 효과 / 연도 / 출처] 표로 정리해 output/cases_table.md 에 저장해 줘.
   - 효과 수치는 파일에 적힌 그대로 옮기고, 수치가 미공개인 사례는 "수치 미공개"로 표시해 줘. 숫자를 지어내지 마.
   - 표 아래에 "진동·온도·압력 중 어떤 센서가 가장 자주 쓰였는지" 한 줄을 적어 줘.
2. data/Day5_설비센서_단위혼재_함정_가상.csv 를 읽고 '기록장치' 열의 값 종류를 보여 줘.
3. 설비별로 평소 값과 단위가 다르게 보이는 행을 찾아 줘. 근거는 기록장치 열과 값의 크기로 설명해 줘.
4. 그 행들을 ℃ · mm/s · bar로 환산해 output/sensor_clean.csv 로 저장해 줘. 열 구조는 원본과 같게 하고, 원본 파일은 수정하지 마.
5. 바꾼 행마다 [설비 / 시각 / 항목 / 기록값과 단위 / 환산값 / 근거]를 output/unit_fix_log.md 에 적어 줘.
6. 끝나면 바꾼 행 수와 cases_table.md 의 사례 수를 알려 줘.
```

### 확인할 것 (Phase B)

- `output/cases_table.md`에 사례 6건이 있고, 효과 수치가 공개된 사례는 4건, 나머지는 "수치 미공개"로 표시돼 있다.
- `output/unit_fix_log.md`에 고친 행이 6개다: 설비A 온도(℉) 3행, 설비B 진동(in/s) 2행, 설비B 압력(psi) 1행.
- 환산값: 설비A 10:00 온도 50.9℃, 설비B 15:00 압력 116.5 bar.
- `output/sensor_clean.csv`가 50행이고 원본 `data/` 파일은 바뀌지 않았다.

막히면 원인을 Claude Code에게 찾게 하는 후속 프롬프트를 준다. 정답은 "정답 보기" 요청이 있을 때만 연다.

```
unit_fix_log.md 에서 바꾼 행 수가 예상과 다르다. 기록장치별로 값의 평균을 비교해서 내가 놓친 행이나 잘못 바꾼 행이 있는지 찾아 줘. 고치기 전에 근거부터 보여 줘.
```

      {"label": "세 행 삭제 후 분석", "description": "명백한 이상치이니 지우고 나머지로 평상 범위를 낸다"}

정답: 2번. ① 세 칸만 같은 교체 로거에서 나왔고, 123.6℉를 ℃로 바꾸면 (123.6 − 32) × 5/9 ≈ 50.9℃로 평소 값과 같다 — 설비가 아니라 기록 단위가 바뀐 것이다. ② 1번은 단위 혼재를 과열로 오인해 멀쩡한 라인을 세운다(가장 비싼 오경보). 3번은 지우는 순간 그 시각의 실제 상태 정보를 잃고, 같은 로거가 계속 ℉로 찍으면 다음에도 같은 일이 생긴다. ③ 현장에서는 로거·측정기를 바꾼 날짜를 데이터와 함께 남기고, 분석 전에 "단위와 측정 주기 먼저"를 체크리스트 첫 줄에 둔다.

### Quiz 2 — 고장 0건인데 왜 바꾸나

```json

정답: 1번. ① 유지보수 단계를 가르는 기준은 "무엇을 보고 정비를 결정하는가"다. 예방 정비(주기)는 안전하지만 상태와 무관하게 교체해 낭비가 크고, 예측 정비(징후)는 필요할 때만 정비해 비용과 정지를 함께 줄인다. ② 2번은 계획 불가·손실 최대인 사후 정비로 후퇴한다. 3번은 원본 강의의 핵심 문장과 반대다 — 예지보전의 가치는 고장을 0으로 만드는 것이 아니라 미리 알아 계획적으로 대응하는 것이다. 4번은 처방 정비도 징후 데이터가 있어야 가능하다는 점을 놓쳤다. ③ 공장장 보고에서는 "교체한 부품 중 실제 마모가 있던 비율"을 한 번 재 보자는 제안이 첫걸음이 된다.
