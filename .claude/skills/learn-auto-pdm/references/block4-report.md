## EXPLAIN

### 1. 보고서 4단과 현장 지표

| 용어 | 뜻 |
|---|---|
| 현황 진단 | 어느 설비·어느 변수가 평상 범위를 벗어났는지 숫자로 |
| 이상 패턴·원인 추정 | 노이즈인지 추세인지, 그 패턴이 어떤 고장 모드와 맞는지. 데이터로 확인 못 한 원인은 반드시 **'추정'** |
| 정비 권고 시점 | 언제까지 무엇을 볼지. 휴무일·부품 조달에 맞출 수 있게 시각과 근거를 함께 |
| 개선안 | 점검 주기와 임계값을 데이터에 맞게 조정하는 것 — **보고서의 핵심** |
| MTBF · MTTR | 고장 간 평균 시간 · 평균 복구 시간. 예지보전 성과는 "MTBF가 늘고 계획 외 정지가 줄었다"로 말한다 |
| OEE | 설비종합효율 = 가용성 × 성능 × 품질. 85%면 세계 최상급 |

### 2. 좋은 보고서와 흔한 보고서

| 기준 | 흔한 보고서 | 오늘 쓰는 보고서 |
|---|---|---|
| 근거 | "진동이 높아 보임" | "설비B 진동 평상 범위 상한을 15:40에 넘음, 15:00부터 연속 상승" |
| 노이즈 처리 | 튄 값마다 "즉시 교체" | 노이즈는 기록·관찰, 추세만 정비 권고 |
| 원인 | 단정 ("베어링 파손") | "감속기 베어링 마모 또는 윤활 부족(추정) — 현장 확인 필요" |
| 개선안 | "점검 강화" | "설비B 진동 측정 주기 20분 → 5분, 3회 연속 상승 시 점검 경보(추정 기준)" |

### 3. 케이스 — 명장은 사라지지 않았다

포스코 스마트 고로에서 AI가 일상 판단과 미세 조정을 맡자 명장들은 AI가 못 푸는 예외·이상 국면의 판단으로 옮겨 갔다. 신입도 데이터 화면으로 노 상태를 읽게 됐다. 예지보전은 보전 기사를 대체하지 않는다. 그들의 오감에 데이터라는 감각을 더한다. 오늘 보고서의 "사람의 역할" 한 단락이 이 이야기다.

### 4. 우리 설비는 4단계 중 어디인가

원본 강의의 마지막 단계(⑥ 평가)는 "오늘 분석한 데이터를 근거로 우리 설비가 사후 → 예방 → 예측 → 처방 중 어디에 있고, 다음 단계로 가려면 무엇이 필요한가"를 묻는다. 기준은 하나다 — **무엇을 보고 정비를 결정하는가.**

## EXECUTE

아래 프롬프트를 붙여 넣으라고 안내한다.

```
pdm-lab 폴더의 분석 결과로 예지보전 보고서를 써 줘.

1. 입력: output/normal_range.csv, output/anomaly_candidates.csv, output/trend_judgement.md. 없으면 멈추고 알려 줘.
2. output/report.md 에 아래 4단 구성으로 써 줘. 모든 수치는 입력 파일에서만 가져오고, 데이터로 확인할 수 없는 원인·효과는 '추정'으로 표시해 줘.
   ① 현황 진단 — 설비별 이상 후보 표
   ② 이상 패턴과 원인 추정 — 노이즈/추세 판정과, 진동·온도가 함께 오를 때 의심할 고장 모드
   ③ 정비 권고 시점 — 설비별로 언제까지 무엇을 할지
   ④ 개선안 — 점검 주기와 임계값 조정안 각 1개 이상
3. 보고서 끝에 "우리 설비의 유지보수 단계" 단락을 붙여 줘. 지금 데이터 수준으로 4단계 중 어디이고, 다음 단계로 가려면 무엇이 필요한지, 예방 정비 대비 예측 정비의 비용·라인 정지 효과를 한 줄로.
4. 보고서 맨 위에 "실습용 가상 데이터 기반" 표시와 핵심 요약 3줄을 넣어 줘.
5. 다 쓴 뒤 스스로 역검토해 줘: "일시적 노이즈를 추세로 잘못 본 부분, 단위를 섞은 부분, '추정' 표시가 빠진 부분이 있는지" 찾아서 고치고, 고친 내역을 보고서 맨 끝 '검토 기록'에 적어 줘.
6. index.html 에 보고서 핵심 요약 3줄과 정비 권고 시점을 카드로 덧붙여 줘. 새 파일을 만들지 말고 기존 파일에 추가해 줘.
```

### 확인할 것 (Phase B)

- `output/report.md`에 ①~④ 머리말 4개와 "유지보수 단계" 단락, "검토 기록"이 있다.
- ① 현황 진단의 이상 후보가 4건이고 Block 2 목록과 같다.
- ② 설비A 진동 12:40 3.5는 노이즈로, "즉시 교체"를 권고하지 않는다.
- ③ 설비B 정비 권고의 근거 시각이 15:00(진동 연속 상승 시작)이다.
- 원인 추정 문장마다 '추정' 표시가 있다.
- `index.html`에 요약 카드가 추가됐고 Block 3 차트가 그대로 있다.

막히면 원인을 Claude Code에게 찾게 하는 후속 프롬프트를 준다. 정답은 "정답 보기" 요청이 있을 때만 연다.

```
report.md 의 숫자 가운데 normal_range.csv, anomaly_candidates.csv, trend_judgement.md 에 없는 숫자가 있는지 한 줄씩 대조해 줘. 출처가 없는 숫자는 지우거나 '추정'으로 바꾸기 전에 목록부터 보여 줘.
```

## QUIZ

### Quiz 1 — 보고서 초안 고치기

```json
AskUserQuestion({
  "questions": [{
    "question": "보고서 초안에 \"프레스 메인모터 진동 3.5 mm/s 측정 — 베어링 파손, 즉시 교체 권고\"라고 적혀 있다. 기록을 보면 3.5는 한 번 찍힌 뒤 다음 측정에 1.0으로 돌아왔고, 온도·압력은 평상 범위 안이다. 어디를 고쳐야 하나?",
    "header": "Quiz 1",
    "options": [
      {"label": "그대로 둔다", "description": "3.5라는 숫자는 실제 기록이니 틀린 곳이 없다"},
      {"label": "판정·원인·조치를 고친다", "description": "노이즈로 판정해 '관찰'로 낮추고, 확인 못 한 '베어링 파손'은 '추정'(측정 오류·순간 외란 가능)으로 바꾼다"},
      {"label": "3.5를 지운다", "description": "노이즈이니 보고서에서 아예 빼서 혼란을 줄인다"}
    ],
    "multiSelect": false
  }]
})
```

정답: 2번. ① 숫자는 맞아도 해석이 틀렸다. 한 번 튀고 돌아온 값은 정비 신호가 아니고, 다른 변수도 평상이라 "파손"을 뒷받침할 근거가 없다. 데이터로 확인 못 한 원인은 '추정'으로 적는 것이 원본 보고서 규칙이다. ② 1번은 숫자의 사실과 판단의 근거를 구분하지 못했다 — 이대로 나가면 멀쩡한 모터를 바꾼다. 3번은 기록을 지워 반복 여부를 추적할 수 없게 만든다. ③ 보전팀은 "어느 설비 어느 부위, 언제까지, 근거"를 원한다. 노이즈는 "관찰 — 반복 시 센서·배선 점검"처럼 조치 수준을 낮춰 적는다.

### Quiz 2 — 개선안 하나만 먼저

```json
AskUserQuestion({
  "questions": [{
    "question": "용접로봇 감속기 진동이 20분 간격 측정에서 세 번 연속 오른 뒤 평상 범위 상한을 넘었다. 다음 주 예산으로 개선안 하나만 먼저 할 수 있다면?",
    "header": "Quiz 2",
    "options": [
      {"label": "주기 단축 + 추세 경보", "description": "이 설비 측정 주기를 줄이고(예: 5분, 추정) '연속 상승 N회' 경보를 더해 추세 시작을 더 일찍 잡는다"},
      {"label": "임계값 올리기", "description": "상한을 높여 경보가 덜 울리게 한다"},
      {"label": "전 설비 센서 추가", "description": "공장 모든 설비에 센서를 더 붙인다"}
    ],
    "multiSelect": false
  }]
})
```

정답: 1번. ① 이 설비의 문제는 "추세를 늦게 알았다"는 것이다. 20분 간격이면 세 번 오르는 데 한 시간이 걸린다. 주기를 고장 진행 속도보다 충분히 짧게 하고 흐름 기준을 더하는 것이 원본 보고서 ④ 개선안(점검 주기·임계값 조정)의 핵심이다. ② 2번은 추세가 보이는 설비에서 경보를 끄는 셈이다. 3번은 원본 보강 실습의 감점 포인트 "센서는 많을수록 좋다 — 목적 없는 계측"이다. ③ 현장에서는 개선안마다 '추정' 기준값과 "언제 다시 볼지(예: 2주 운영 후 재조정)"를 함께 적는다.
